SnackPay
Cashless School Cafeteria Platform

A multi-tenant, cloud-native platform that lets parents fund and control their children's cafeteria spending, removes cash from the lunch line, and gives schools an offline-tolerant point of sale. This document is layered: an executive narrative up top, deep technical architecture below, structured around the C4 model.

Cloud · Google Cloud (GKE) Services · Go microservices Tenancy · Shared schema · Row-Level Security IDM · Keycloak POS · Offline-first · BYOD Billing · Subscription + usage Local · one command

01Executive Summary

SnackPay replaces cash in the school cafeteria with a prepaid, parent-controlled digital wallet tied to each child. Parents top up an account, pre-order meals, and see exactly what their child buys — in real time. Schools get a fast, mistake-free, queue-reducing point of sale that keeps working even when the internet drops.

0
cash handled at the counter — eliminates change errors & bullying over money
<3s
target POS transaction time via QR scan + pre-authorised wallet
100%
parent visibility into every purchase, with per-item history

The business model is B2B2C SaaS: schools (tenants) subscribe; parents and cafeteria staff are the end users. A single platform instance serves many schools securely via row-level tenant isolation. Phase 1 delivers the web/PWA experiences, the offline-capable POS, the wallet ledger, QR issuance, and subscription billing. The native mobile app is deferred to Phase 2; for now, parent notifications and WhatsApp messages are simulated through a pluggable notification gateway so the product can be demonstrated end-to-end without third-party costs or approvals.

Reading guide. Sections 01–04 are for everyone (stakeholders & engineers). Sections 05–08 (C4 & flows) suit both audiences. Sections 09+ are engineering deep dives — data model, offline sync algorithm, QR, billing, security, and local dev.

02Problem & Solution

Today's Pain

  • Parents forget to send money; children go without.
  • Reluctance to hand young children cash for fear of loss.
  • Change mistakes pile up during the interval & lunch rush.
  • Manual handling creates long queues and lost class time.
  • Parents have zero visibility into what's actually bought.
  • Cash handling exposes children to bullying and coercion.

SnackPay Delivers

  • Pre-order interval/lunch from a phone or browser.
  • Top up any time at the cafeteria counter.
  • Live view of every item a child purchases.
  • Running balance + full top-up and order history.
  • A QR card replaces cash — nothing to steal or lose value from.
  • Fast scan-and-go line that keeps flowing offline.

The core loop, told plainly

A parent visits the cafeteria and tops up their child's account; the cashier records it and the child receives a QR card. The top-up appears instantly in the parent's app. The parent browses the menu and, if they wish, pre-orders the child's interval or lunch. During the school day the child presents the card; the cashier scans it, hands over the item, and marks it delivered. The parent sees "delivered," the item's price moves from the child's prepaid wallet into the cafeteria's account, and the purchase lands in the child's history. Every step is an event the platform records, reconciles, and can replay.

04Guiding Principles & Requirements

Architectural Principles

  • Money is sacred. The wallet is an append-only, double-entry ledger — balances are derived, never edited in place.
  • The line never stops. POS degrades gracefully offline and reconciles deterministically.
  • Tenant-safe by construction. Every query is tenant-scoped at the database, not just the app.
  • Event-first. Domain events are the source of truth for notifications, history, and reconciliation.
  • Swap-able edges. Payments, notifications, and identity sit behind interfaces so vendors can change without core rewrites.
  • Runs on a laptop. The entire system boots locally with one command.

07C4 · Level 3 — Components (Wallet / Ledger)

Zooming into the most safety-critical service. The ledger never mutates a balance; it appends double-entry postings and derives balances, guaranteeing money can always be reconciled.

Component (in-process) Owned store / bus Shared infrastructure
Figure 3 — Components of the Wallet/Ledger service. A posting request is deduped (Idempotency Guard), checked (Funds Policy), appended (Ledger Repository), reflected in a cached balance (Balance Projector), and announced (Event Publisher). Holds back pre-orders; a Reconciliation Job proves the books.
Why double-entry? Every transaction writes two rows — a debit and a credit — that must sum to zero across accounts (child wallet, cafeteria account, top-up source). Balances are a projection over entries, so a corrupted cache can always be rebuilt, and every cent is auditable per tenant.

12Multi-Tenancy & Isolation

One platform, many schools. We chose the shared-schema, row-level-security model: a single Postgres database with a tenant_id on every tenant-owned row and Postgres RLS policies that make cross-tenant reads impossible even if application code has a bug.

Isolation layers (defence in depth)

  • Identity: Keycloak realm per tenant; the JWT carries a tenant_id claim.
  • Edge: API Gateway resolves & verifies the tenant from the token and host, and stamps it on the request context.
  • App: every repository call runs inside a tenant-scoped transaction that first executes SET LOCAL app.tenant_id = $1.
  • Database: RLS USING (tenant_id = current_setting('app.tenant_id')::uuid) on every table — the DB itself refuses foreign rows.
  • Storage: object keys and Pub/Sub message attributes are tenant-prefixed; consumers assert the tenant.

Why not schema/DB-per-tenant?

At school scale (hundreds–thousands of pupils each) per-tenant databases multiply migration, backup and connection-pool overhead for little benefit. Row-level security gives strong, DB-enforced isolation at a fraction of the ops cost, and keeps a single migration path. If a large tenant later needs physical isolation, the model allows promoting them to a dedicated schema/DB without changing service code — the tenant resolver just points them at another datasource.

RLS in practice

-- every tenant table
ALTER TABLE ledger_entry ENABLE ROW LEVEL SECURITY;
ALTER TABLE ledger_entry FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON ledger_entry
  USING     (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- Go: per-request, inside a tx, before any query
tx.Exec(ctx, "SET LOCAL app.tenant_id = $1", tenantID)
Guardrail. The service DB role is non-superuser and non-BYPASSRLS, so even a raw query cannot escape the policy. A CI test asserts that querying without setting app.tenant_id returns zero rows.

13Data Model

Core entities. Every tenant-owned table carries tenant_id (omitted from the diagram for clarity). The wallet is modelled as accounts + immutable ledger entries.

Figure 8 — Core data model. A Child owns one Account (wallet); the cafeteria and top-up sources are also Accounts. Every money movement writes balanced LedgerEntry rows sharing a txn_id; Holds reserve funds for open Orders. Balances are cached but always re-derivable from entries.

Key data rules

  • Immutability: ledger_entry is insert-only; corrections are reversing entries, never updates or deletes.
  • Balanced transactions: a DB constraint/check ensures all entries with the same txn_id sum to zero.
  • Idempotency: a unique index on (tenant_id, idempotency_key) makes retries and offline replays safe.
  • Money type: integer minor units (e.g. cents) — never floats.
  • Auditability: every event is stored in an outbox table and published via the transactional outbox pattern, so DB state and events never diverge.

14Offline & BYOD POS — the Algorithm

The POS is a PWA installed on staff-owned devices (phones/tablets). A service worker caches the app shell and menu; an IndexedDB queue holds transactions made while offline. The design goal: never block the line, and never lose or double-apply a transaction.

How the POS stays safe offline

  • Signed balance snapshots. While online, the server pushes each child's balance + offline_limit as a short-TTL, server-signed token. The POS verifies the signature offline — it can trust the number without trusting the device.
  • Bounded exposure. Offline spend per child is capped by offline_limit (e.g. one day's typical spend), so even worst-case multi-device overspend is small and recoverable.
  • Local ledger. Each offline sale is written to IndexedDB with an idempotency_key, monotonically increasing clientSeq, timestamp, and the child/QR reference.
  • Deterministic replay. On reconnect the queue is POSTed as a batch; the server applies each txn idempotently and returns per-item results.
  • Exception surfacing. Rejections (insufficient funds discovered at reconciliation) are flagged to staff/admin, not hidden — the child already ate, so it becomes a small receivable, not a silent loss.

Conflict resolution

Because two BYOD devices could both sell to the same child while offline, the server is the arbiter. It replays txns ordered by (serverReceiveTime, clientSeq), applying the Funds Policy against the true ledger balance. First-wins for available funds; overspend beyond a released hold is recorded as an exception with the responsible order/device, and admins get a reconciliation report. The offline_limit keeps this rare and cheap.

Sync contract (server side, simplified)

POST /api/pos/sync            Authorization: Bearer <pos-jwt>   Tenant: <realm>
{
  "deviceId": "pos-abc",
  "transactions": [
    { "idempotencyKey":"7f3a…", "clientSeq": 412, "childId":"…",
      "qrToken":"…", "items":[{"menuItemId":"…","qty":1}],
      "amountMinor": 350, "occurredAt":"2026-07-11T09:14:03Z" }
  ]
}
=> 200
{ "results": [
    { "idempotencyKey":"7f3a…", "status":"applied",   "txnId":"…" }
    // or "duplicate" (already applied) | "rejected" (reason: insufficient_funds)
  ],
  "snapshotRefresh": [ { "childId":"…", "balanceMinor": 1250, "offlineLimitMinor": 500,
                         "sig":"…", "exp": 1752… } ]
}
Idempotency is the whole trick. The client may resend a batch after a flaky connection; the unique (tenant_id, idempotency_key) index means a second apply is a no-op that still returns applied/duplicate, so the POS can safely retry until it gets an ack.

15QR Card Lifecycle & Printing

The QR card is the child's physical key to the cafeteria. It carries an opaque, signed reference — never a balance or personal data — so a lost card leaks nothing and can be revoked and reissued in seconds.

Figure 9 — QR card state machine. A card is issued and printed, bound to a child, then Active. It can be Suspended (temporary) or Revoked (lost/stolen); revocation invalidates the token instantly and a Reissued card gets a fresh token. Old scans fail closed.

What's on the card

The QR encodes a compact URL/opaque token like snackpay://c/<cardId>.<nonce>.<sig>. The signature (HMAC/asymmetric, per-tenant key) lets the POS verify authenticity offline. The server stores only a hash of the token. No name, balance, or PII is printed — just the child's display name/photo optionally for the cashier, per school policy.

Printing pipeline

  • QR Service renders a print-ready PDF/PNG (card front: QR + child name/grade + school branding) and stores it in GCS.
  • Admin Console prints in-browser to any local/thermal/label printer, or batch-exports a sheet of cards for a class.
  • Card stock options: PVC card, adhesive label, or lanyard tag — all just carry the same QR.
  • Reissue reprints with a new token and auto-revokes the old one.

16Subscription & Billing

Schools (tenants) subscribe to a plan. The Billing service owns plans, subscriptions, usage metering and invoices, and talks to a payment provider through a thin adapter so the PSP can change without touching core logic.

Figure 10 — Subscription lifecycle. Trials convert to Active; failed charges enter dunning (Past Due) and, if unresolved, Suspended (read-only) then Cancelled. Suspension degrades gracefully — the cafeteria can still operate briefly to avoid stranding pupils.

The PaymentProvider is an interface (Charge, Refund, Webhook); a Stripe-style adapter implements it in production, and a fake in-memory adapter implements it locally so billing flows are fully testable offline. Invoices and usage records are per-tenant and exportable.

17Notifications — Simulated in Phase 1

Every parent-facing message (top-up received, order placed, delivered, low balance) flows through one Notification Gateway with pluggable channel drivers. In Phase 1 the WhatsApp and push drivers are simulators: they render and persist the exact message that would be sent, so the product demos end-to-end with zero third-party dependencies or cost.

type Channel interface { Send(ctx, msg Notification) (Receipt, error) }

// Phase 1 — swap-in simulators behind the same interface
type SimWhatsApp struct{ store Repo }        // records "sent", visible in admin + logs
type SimPush     struct{ store Repo }        // no-op delivery, full audit trail
// Phase 2 — real drivers, no caller changes
type TwilioWhatsApp struct{ /* ... */ }
type FCMPush        struct{ /* ... */ }
Why simulate rather than stub-out. The simulators traverse the real event → gateway → template → "delivery" path and store an outbox of messages. When you later drop in Twilio/Meta and FCM, nothing upstream changes — you flip a config flag per tenant. Simulated messages appear in the admin console and the parent's in-app inbox, so the experience is complete today.

18Security & Compliance

Identity & access (Keycloak)

  • OIDC/OAuth2; realm per tenant for user isolation.
  • Roles: parent, cashier, school_admin, platform_admin.
  • Short-lived access tokens + refresh; POS devices get scoped, revocable device tokens.
  • Gateway validates JWT signature, audience, expiry and tenant_id claim on every request.

Data protection

  • TLS everywhere; secrets in GCP Secret Manager.
  • Postgres RLS + non-superuser roles enforce tenant isolation at the DB.
  • Encryption at rest (Cloud SQL, GCS) and PITR backups.
  • Children's data minimised: QR carries no PII; least-privilege access; per-tenant audit logs.
  • Child-safety by design — parents control spend; no direct child payment surface.

Financial integrity

  • Immutable double-entry ledger; balanced-transaction constraint.
  • Idempotency keys across API + offline sync prevent double-spend/credit.
  • Nightly reconciliation proves ∑debits = ∑credits per tenant.
  • Bounded offline limits cap worst-case exposure.

Platform hardening

  • Cloud Armor WAF, rate limiting at the gateway.
  • Signed container images from Artifact Registry; least-privilege workload identity.
  • Structured audit trail via the event outbox.
  • Data-residency friendly — regional GKE + Cloud SQL; per-region deploys possible.
Compliance posture. Because pupils are minors, the design favours data minimisation, parental control, regional data residency, and full auditability — a solid base for GDPR-style and local education-data obligations. Formal certification is out of scope for this blueprint but nothing here blocks it.
